# Rubric: Model parameter

If the learner misses a question here, set a DEFINE or INTERPRET move for model parameter live, as
help (it is recorded as helped and doesn't count), then come back to a production question.

A model parameter is a value chosen before a simulation runs that the model's rules use: change one
and the model behaves differently. A simulation outcome is the other way round: it comes out of a
trial, and nobody sets it. A parameter is a value, not the edge of what the model covers (that is
what the model leaves out), not a chance event the rules settle during a run, and not a value the
rules never use, however much it matters in the real world.

### catch-limits

- **goal:** `w-model-parameter`
- **move:** CATCH
- **answer:** Snow but not ice, main roads but not side streets, are what the model leaves out, its
  scope, not its parameters. A model parameter is a value chosen before a run that the model's
  rules use, such as the number of plows or how fast the snow falls; change one and the model
  plays out the storm differently.
- **credit:** full for naming that the limits are what the model covers or leaves out, not
  parameters; saying what a parameter is (a value set before a run that the rules use) is welcome
  but not required. Half for a correct parameter named without saying why the limits aren't
  parameters. None for a different quibble alone, such as that the model ought to
  cover ice.
- **tutor note:** "within these parameters" means "within these limits" in everyday speech, which
  is where this comes from; if the learner defends it on those grounds, ask what the plow model's
  rules need to be told before a storm can be played out.

### vs-outcome

- **goal:** `w-model-parameter`
- **move:** DISTINGUISH
- **answer:** A model parameter is a value chosen before a run that the model's rules use: here,
  the number of drivers on shift (and the rate orders come in). A simulation outcome is what a
  trial produces that the question cares about: here, how many pizzas arrived late that Friday.
  The shop sets the drivers; it doesn't set the late pizzas, the trial tells it.
- **credit:** full for naming that a parameter goes in, chosen before the run, and an outcome
  comes out of a trial; examples from the pizza shop are not required, but any given must be
  matched correctly, and a mismatched one makes it half. Half also for "parameters are what you
  control and outcomes are results" with no word on when each is fixed, before or by the run. None
  for an incidental difference alone, such as that outcomes vary from trial to trial and
  parameters don't.

### catch-pick

- **goal:** `w-model-parameter`
- **move:** CATCH
- **type:** mcq
- **answer:** 2
- **credit:** full for 2 only. The number of reservations accepted is chosen before the run, and
  the rules use it, so it is a model parameter. Choice 1 is the simulation outcome: the trial
  produces it, and wanting it low doesn't make it something set beforehand. Choice 3 is a chance
  event the rules settle during the run; the parameter is the 9 in 10 chance, not each guest's
  draw. Choice 4 may matter to the real hotel, but this model's rules never use it.
- **tutor note:** a learner who picks 3 has seen that chance is in the rules; ask which number in
  the setup is fixed before the night starts and which is drawn as it goes.
